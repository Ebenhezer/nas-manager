# Security

Status after Phase 14: all fourteen phases are implemented. Phase 14 added the hardening below (drop-folder rate limiting before the body is read, explicit proxy and Host trust, HSTS/Permissions-Policy/COOP/CORP, bounded CSRF buffering, a tighter unit sandbox, dependency scanning) and the first live deployment under systemd, which found and fixed four deployment bugs (helper socket directory not traversable, `@mount` missing from the helper's syscall filter, the helper mounting inside a private mount namespace, every pre-existing mount point refused). Phase 13 added syslog and comprehensive auditing; Phase 12 configuration export/import with sealed secrets, validation and rollback. Encrypted, deduplicated, versioned backups with verification, retention and restore (Phase 11) run in the unprivileged worker. System monitoring and alerting (Phase 10) runs there too, with email/webhook channel secrets encrypted at rest. Before that, a photo gallery with private personal libraries and group-granted shared libraries (Phase 8) and video streaming with sandboxed ffprobe/ffmpeg and cached transcodes (Phase 9) are implemented on top of the earlier phases. Since Phase 7, remote and cloud synchronization (SFTP, FTP/FTPS, WebDAV, S3, Google Drive) runs in a separate unprivileged worker with credentials encrypted at rest and a no-delete sync policy; sessions, scoped personal API tokens, RBAC, CSRF and audit logging are in place; the file manager (path-jailed, with resumable uploads and a change journal for sync), Samba share management (validated, merged config), the public upload folder (upload-only, atomic per-uploader and per-token quotas) and disk/storage/RAID management (read-only discovery; confirmed, intent-bound actions through a root helper) are implemented. All management pages and the interactive dashboard require authentication.

## Controls in place

| Control | Detail |
|---------|--------|
| Authentication | Argon2id password hashing (RFC 9106 low-memory profile, costs configurable). Server-side sessions; the database stores only SHA-256 of the session and CSRF tokens. Passwords are never stored, logged or echoed (tests assert it). |
| Login abuse controls | Per-account lockout after N failures (persistent) and a per-IP sliding window (`429` + audit event). Tested. |
| Sessions | `HttpOnly` cookie, `SameSite=Lax` (configurable), optional `Secure` (required when TLS terminates in front). Hard TTL plus idle ceiling; revocation on logout, password reset and deactivation. Changing your **own** password keeps your other sessions and API tokens (a deliberate choice, design decision 19, re-confirmed in Phase 14): revoke them from Profile (tokens) or have an administrator reset the password, which revokes both. |
| CSRF | Double-submit cookie + session-bound token digest. Form field `_csrf` and `X-CSRF-Token` header both supported; first-page-load regression is tested. Cookie-less API clients and `Authorization: Bearer` requests are not CSRF-checked: they are authenticated by the header alone (cookies are ignored), and a browser cannot attach that header cross-site without a CORS grant, which the app never issues. Tested. |
| API tokens | `nas_` + 256 bits of randomness; only SHA-256 is stored and the raw value is shown once. Effective access = token scopes ∩ the owner's current permissions (re-evaluated per request), so a token never exceeds its owner and shrinks when the owner loses a role. Scopes outside the creator's permissions are refused. Mandatory expiry by default (`NAS_API_TOKEN_MAX_LIFETIME_DAYS`), per-user cap, revocation by owner or admin, automatic revocation on admin password reset and deactivation. Tokens cannot mint/revoke tokens, change the password or log out (session-only endpoints). An `Authorization` header is authoritative: a bad value is 401, never a fallback to the cookie. Failed lookups are rate limited per IP (429) and audited up to the limit. Web pages stay cookie-only. Tested. |
| Resumable uploads | Destination validated with the same jail and name rules at creation and re-checked at completion; size caps enforced at creation and per chunk; chunks are bounded, offset-checked (409 on mismatch), fsync'ed before the offset advances and rolled back on any limit violation; optional SHA-256 verification discards mismatching data; uploads are private to their owner (404 otherwise); `files:write` is re-checked on every step; expired uploads are swept. Public-target quotas are reserved under the same row lock as single-shot uploads at completion. Tested. |
| Authorization | Permission tokens (`dashboard:read` … `api_tokens:write`) granted through roles; effective permissions = direct roles + the roles of the user's groups. API routes deny by `require_permission`, web pages by permission checks. Tested per role. |
| Last-administrator safety | Cannot delete or deactivate your own account; cannot demote the final administrator; deleting a group that is the only vehicle of admin power is refused. Tested. |
| Audit trail | Append-only `audit_events`: actor (survives user deletion by username snapshot), outcome, target, IP, user agent and request id for every auth/user/group/role change. |
| Unprivileged process | systemd unit runs as `nas-manager`, empty capability set, `NoNewPrivileges`, `ProtectSystem=strict`, private `/tmp` and devices, syscall filter. |
| No secrets in code or repo | `.env.example` and `deploy/nas-manager.env.example` hold no real values; `.env` is git-ignored; the bootstrap password is only ever read from a prompt or stdin. |
| Log redaction | Sensitive extra-field names are replaced with `***` in all handlers (tested). Query strings are never logged. |
| Request-id validation | Client ids restricted to `[A-Za-z0-9-]{1,64}` to prevent log injection (tested). |
| Security headers | `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, and `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; object-src 'none'` (tested). |
| CSP-compatible UI | No inline script or style; DOM is built with `textContent` (no `innerHTML`). A test fails if inline code appears. |
| File manager path jail | Every requested path is resolved against a configured managed root and rejected when it escapes (`..`, absolute paths, null bytes, symlinks resolving outside the root). Listing/search never follow symlinks; uploads stream to a temp file and are atomically renamed, and the per-file cap (`NAS_MAX_UPLOAD_BYTES`) is enforced mid-stream so concurrent uploads cannot bypass it. Tested, including symlink escape. |
| Public upload folder | Upload-only: there is no public listing, download or search endpoint; the public policy endpoint exposes only the enabled flag and the per-file cap. Filenames are sanitized (no separators/`..`/null bytes, ≤ 255 bytes) and auto-uniquified — the folder never overwrites. Files land in digest-named per-uploader directories; API-token clients are charged to their own `token:<id>` quota; per-file and per-uploader quotas are enforced atomically inside the transaction that records the file (the uploader's quota row is locked first), so concurrent uploads cannot bypass a quota and a rejected upload consumes nothing and leaves no temp file. Deletion paths are re-verified against the upload root. Tested. |
| Samba config safety | The DB is the source of truth; `smb.conf` is only touched inside the managed markers, validated with `testparm -s` against a temp copy before writing, backed up first, written atomically. Free-text share fields reject newlines (no config injection); share names are restricted to `[a-z0-9][a-z0-9._-]*`. When the privileged helper is enabled, Apply delegates the write + `smbd` reload to it (which re-validates with `testparm`, backs up and writes atomically before reloading). Tested. |
| Privileged helper isolation | The web process never runs as root and holds no capabilities. All privileged work happens in a separate helper bound to a fixed allowlist of 14 validated operations over a Unix socket (`SO_PEERCRED` UID check + `0660 root:<group>` socket; responses and requests are length-prefixed JSON, max 1 MiB). The helper never executes client-supplied commands or option flags: device names cannot start with `-`, mount points must be absolute and normalised, filesystem types and option tokens are allowlisted (options `loop`/`bind`/`rbind`/`remount` refused), RAID devices must exist under `/sys/block/md*`, and `samba.apply` only ever writes the configured `smb.conf` path after requiring the managed markers. Tested. |
| Confirmed destructive operations | Nothing is ever mounted/unmounted or scrubbed without the API user explicitly confirming (`confirm: true` on the action call), after a `…/preview` endpoint has shown the exact plan and warnings. The action is bound to the previewed parameters by a deterministic intent digest that the helper re-derives from its own re-validated parameters; mismatches are refused. RAID scrub only ever writes `check` (never `repair`) to `md/sync_action`. Tested. |
| USB / removable drives (Phase 16) | Only partitions of hot-plugged disks (`TRAN=usb`, `RM` or `HOTPLUG`) with an allowlisted file system are auto-mounted. Internal disks, RAID members, LUKS, swap and anything in `/etc/fstab` are never touched. The helper picks the mount point (`NAS_REMOVABLE_MOUNT_DIR/<sanitised label>`) and the options itself: always `nosuid,nodev,noexec`, plus `root:<service group>` with mode `0770`/`0660` on FAT/exFAT/NTFS; clients cannot pass any. Device names from `lsblk` are re-validated before `mount`. Vanished devices are lazily unmounted. Users need `removable:read` / `removable:write` (admin and operator by default) to see or copy to a drive, separately from `files:*`, so an admin can stop data leaving the NAS on a stick. USB drives can never become shares, libraries or backup targets. Copies are fsynced and flushed; mount, unmount and copy events are audited. Tested. |
| Least privilege / operator toggle | `operator`/`viewer` cannot open Files/Samba by default. Admin may flip `operator_view_files_samba` in Settings to grant operators read-only access; the toggle never grants write permissions and is audited. Operators receive `disks:read` (read-only discovery) only; mounting/unmounting/scrubbing requires `disks:write` (admin by default). Tested. |
| Remote credentials at rest | Passwords, SSH private keys and passphrases, S3 secret keys, OAuth client secrets and refresh tokens are stored only as one Fernet token (AES-128-CBC + HMAC-SHA256) per connection. The key lives in `NAS_CREDENTIALS_KEY_FILE` (default `<data_dir>/secrets/credentials.key`), created atomically with mode 0600 in a 0700 directory; a key file readable by group/others is refused. The API never returns secret values (only which fields are set); PATCH keeps omitted secrets; audit details list field names only. Creating/updating connections, probing host keys and the OAuth flow are session-only (API tokens get 403). Verified in tests and in the live run: the password does not appear in the database, WAL, logs or audit log. |
| Remote transport security | SFTP connects only to the pinned host key (`RejectPolicy`; a changed key aborts before authentication); the key is fetched with a probe and must be confirmed by an administrator after comparing the fingerprint. FTPS uses `AUTH TLS` + `PROT P` with certificate verification; plain FTP and plain-HTTP WebDAV/S3 endpoints are refused unless the connection explicitly sets `allow_insecure`. URLs may not embed credentials. Google Drive uses OAuth 2.0 authorization code + PKCE; the state is random, stored hashed and encrypted, single-use, bound to the initiating user and valid for 10 minutes. Tested. |
| Sync data safety | Nothing is ever hard-deleted by sync. One-way jobs never overwrite a destination that changed (reported instead). Conflicts keep both versions by default; `prefer_*` policies move the losing version into `.nas-sync-archive/` before overwriting. Deletions are reported (default) or archived, never propagated as deletes; a deletion against a modification restores the file. A deletion guard fails a run before any action if it would archive more than `NAS_REMOTE_SYNC_MAX_DELETE_COUNT` files or `NAS_REMOTE_SYNC_MAX_DELETE_PERCENT` of the synced set; overriding it, enabling a job, two-way mode, archiving and `prefer_*` policies all require `confirm: true`. Every conflict, archive and guard trip is audited. Dry runs show the full plan without touching anything. Tested. |
| Remote input validation | Remote names are untrusted: entries with separators, `..`, control characters or over-long names are rejected and reported, never mapped to local paths; every local write is re-checked against the file-manager jail and the job's directory; downloads are staged and moved atomically; symlinks are never followed or synced. WebDAV XML is parsed without external entities and size-capped. Tested with hostile listings. |
| Sync worker isolation | The worker is a separate process under the same unprivileged account and systemd sandbox as the web unit (no capabilities, `ProtectSystem=strict`); it refuses to start on an outdated schema. Runs hold leases so a crashed worker's run is reclaimed, never executed twice concurrently. |
| Media access control | Personal libraries are browsable only by their owner — administrators see the library *record* (counts, scan state) but cannot open other users' photos; shared libraries are browsable by members of the granted groups and by `media:admin`. Every item, thumbnail, original, stream, transcode and album lookup is filtered by the same SQL clause, so an item outside the caller's libraries is a 404 (no ID probing). Albums are private to their owner and never expose items whose library access was revoked. Uploads and deletions are allowed only in your own personal library (`media:write`); shared libraries are read-only through the gallery. API tokens need `media:*` scopes. Tested per role, per token scope and across users. |
| Media path jail | Library folders are re-resolved through the file-manager jail (`resolve_root` + `resolve_in_root`) on every use; personal libraries live under `NAS_MEDIA_DIR/<username>` (usernames are immutable and validated). Scans never follow symlinks and skip hidden entries; every served original is re-checked inside its library. Upload names and folders are sanitized (no separators, `..`, hidden parts, > 8 levels); names are never overwritten (hard-link placement, collision suffixes). Tested, including symlink escapes. |
| Media file serving | Originals are served with a type from an extension allowlist (JPEG, PNG, GIF, WebP, BMP, TIFF, HEIC/HEIF and common video containers), never sniffed, with `X-Content-Type-Options: nosniff`; SVG and HTML are not media types here, so an uploaded file cannot become an active document on the application's origin. Thumbnails are re-encoded WebP generated server-side. Tested. |
| Image decoding limits | Pillow only decodes images whose header-declared size is within `NAS_MEDIA_MAX_IMAGE_PIXELS` (default 100 MP); Pillow's decompression-bomb warning is promoted to an error. Corrupt files and corrupt EXIF never crash a scan (the item is indexed with `thumb_state: failed`). JPEG thumbnails decode at reduced scale (`draft`). Tested with oversized and corrupt files. |
| ffmpeg isolation | ffprobe/ffmpeg run only from `app/services/media/ffmpeg.py`, in the worker for posters and transcodes and in the web process for probing uploads: fixed argument lists, no shell, every input/output passed as `file:<absolute path>` (a hostile name such as `-i http:…` stays a local file name), minimal environment, `stdin=/dev/null`, timeouts (`NAS_MEDIA_PROBE_TIMEOUT_SECONDS`, `NAS_MEDIA_TRANSCODE_TIMEOUT_SECONDS`), killed on worker shutdown. Transcodes are written to a temp file and renamed; outputs are keyed by a source fingerprint so a changed file never streams a stale rendition. The worker unit runs at `Nice=10` with best-effort I/O priority 7. Tested with a fake binary and against the real ffmpeg 6.1. |
| Monitoring privilege boundary | Monitoring runs in the unprivileged worker, and the web process only reads stored snapshots. Service state comes from unprivileged `systemctl show`. Unit names come from configuration and are validated twice: by `NAS_MONITOR_SERVICES` at load and per call, with no leading `-`, no separators and a known unit suffix. They are passed after `--` with no shell, a minimal environment and a timeout. RAID state is read from `/proc/mdstat`. SMART reuses the helper's existing `disk.list`/`disk.smart` operations, and **no operation was added to the root allowlist**. Tested with hostile unit names. |
| Process list exposure | `GET /monitoring/processes` (`system:read`) returns PID, name, user, state, CPU and memory only. **Command lines and environments are never collected**, because they routinely carry passwords passed as arguments. Tested. |
| Alert channel secrets | The SMTP password, the webhook signing secret and the webhook `Authorization` value are one Fernet token per channel, using the same key file as remote credentials. Responses list only the names of set secret fields. PATCH keeps omitted secrets. Audit details carry field names, never values. Create, update and test are session-only (API tokens get 403). Unknown config fields are rejected, so a secret cannot end up in the clear `config` column by mistake. Tested, including a scan of the stored row and the audit log. |
| Notification transport | SMTP uses STARTTLS or implicit TLS with a default (verifying) SSL context. Webhooks must be HTTPS. Plain SMTP and plain HTTP are refused both when saved and when sent unless the channel sets `allow_insecure`. Webhooks never follow redirects, so a 30x to an internal address is a failed delivery, not a request. URLs may not embed credentials. Addresses must be single-line `local@domain` values, and messages are built with `EmailMessage` with the subject whitespace collapsed, so header injection is not possible. Webhook bodies contain alert fields only. Tested. |
| Backup encryption | Every repository is encrypted before data leaves the process: scrypt (cost `NAS_BACKUP_SCRYPT_N`, stored parameters are bounds-checked so a hostile `repo.json` cannot demand unbounded work) → HKDF-SHA256 content and naming keys → AES-256-GCM in 4 MiB segments with a random 96-bit nonce per segment and the segment index plus final flag as associated data. Tampering, truncation, reordering, trailing data and wrong passphrases are rejected (tested). Blob names are keyed HMACs of the content hash, so a storage provider cannot confirm whether a known file is stored; it does see blob sizes, counts and timing. |
| Backup passphrases | Stored only as a Fernet token (same key file as remote credentials), never returned, logged or audited (`passphrase_changed: true` at most). Create and update are session-only (API tokens get 403). Losing the passphrase makes the repository unreadable by design; losing the credentials key only means re-entering the passphrase. Tested, including a scan of the stored row, the audit log and, in the live run, the database, WAL, logs and repository files. |
| Backup deletion boundary | The provider `delete` primitive exists only for retention and garbage collection inside a repository and is never called by sync. Retention removes only snapshots of jobs with a policy; garbage collection deletes nothing unless every snapshot is readable. Real prunes need `confirm: true`. Deleting a repository or job in the app never touches the target. A repository is only created by an explicit *Initialize* into an empty or new folder (a non-empty foreign folder is refused), and a missing `repo.json` fails the run instead of re-creating the repository, so an unmounted disk never receives a backup on the root filesystem. |
| Restore safety | Restores never delete. By default they write into a new folder and skip existing files; replacing needs `overwrite` + `confirm`, and the previous versions are moved to `.nas-backup-replaced/<timestamp>/`. Paths from manifests are re-validated and jailed (`..`/absolute paths are refused and reported, tested with a crafted manifest), every file is checked against its SHA-256 before an atomic rename, and permission bits are masked to `0777` (no setuid/setgid). Restores require `backup:restore` (admin only by default); operators can view backups but not restore or cancel restores. |
| System restore boundary | The web process and worker never replace the live database. A system snapshot is staged with checksums and installed by `python -m app.cli restore-system --yes` with the services stopped; the CLI re-verifies checksums, keeps the replaced files as `*.before-restore-<timestamp>`, migrates and audits. `backup-recover` reads the passphrase from a prompt or stdin only and restores only into an empty directory. |
| Configuration exports | Secrets leave the system only when the administrator gives an export passphrase, and then only sealed (scrypt + AES-256-GCM) together with a SHA-256 of the readable sections, so a modified file is refused on import. Without a passphrase, password hashes, credentials, channel secrets and backup passphrases are omitted (tested by scanning the file). Export and import are admin-only and session-only (API tokens get 403); exports are audited with object counts. |
| Configuration imports | Documents are untrusted: types, sizes and every value are validated with the same validators as the API (names, permissions, paths jailed to file roots and backup roots, provider and channel rules, alert thresholds); unknown sections are refused; password hashes must be Argon2. Imports are all-or-nothing in one transaction, previewable without side effects, and refused if no administrator would remain or the importing user would lose admin rights. Risky effects (enabled jobs, deletions, guest shares) need confirmation. Deactivated users have their sessions and tokens revoked in the same transaction. `smb.conf` is never written by an import. |
| Configuration rollback | Each import keeps an encrypted (credentials key) pre-import snapshot and a database copy (`0600`, last 10 kept). Rollback is confirmed, limited to the latest import, and transactional. |
| Static file serving | Path traversal attempts against `/static` return 400/404 (tested). |
| Error hygiene | Unhandled exceptions return a generic 500 envelope with a request id and no internals (tested). |
| API docs | Swagger/OpenAPI disabled unless `NAS_DEBUG=true`. |
| Dependencies | Fully pinned runtime set in `requirements.txt` including `argon2-cffi`, `python-multipart`, `cryptography`, `paramiko`, `boto3`, `httpx2` and `Pillow`. ffmpeg is a system package (Ubuntu `ffmpeg`), kept current by the OS's security updates. |
| Audit integrity (Phase 13) | The worker seals audit events into a SHA-256 hash chain; `POST /audit/verify` (and a daily worker check) detects edited, deleted, re-ordered or truncated events and unsealed events inside the sealed range, and records `audit.chain_broken`. The chain is tamper-*evident*, not tamper-proof: someone who can write the database can recompute it and the anchor/head settings. A remote syslog destination keeps the off-host copy that settles such disputes. |
| Remote syslog (Phase 13) | TLS (default) always verifies the collector's certificate and host name (system store or a per-destination CA); there is no "insecure TLS". Plain UDP/TCP require an explicit confirmation listing the risk. Destinations hold no secrets. Audit events are forwarded at-least-once from a cursor; syslog has no application-level acknowledgement, so a collector that crashes mid-batch can lose that batch (RELP is not supported). Application logs are forwarded best effort through a bounded queue (drops are counted) and go through the same redaction as every other output. |
| Drop-folder rate limit (Phase 14) | `POST /public/uploads` is admitted by a middleware **before FastAPI parses the multipart body** (which would otherwise spool the whole file to disk): a declared `Content-Length` above the per-file cap (+64 KiB framing) is a 413 `payload_too_large`; more than `NAS_PUBLIC_UPLOAD_RATE_MAX_REQUESTS` uploads per uploader (`ip:`, `user:` or `token:`) per `NAS_PUBLIC_UPLOAD_RATE_WINDOW_SECONDS` (default 30 per 5 min) is a 429 with `Retry-After`; an uploader with no quota left is a 413 `quota_exceeded`. The first rejection per uploader and window is audited (`public_upload.rate_limited`), so a flood cannot fill the audit log. The guard runs inside the CSRF check, so a forged cross-site request cannot use up a victim's allowance. The locked quota check at commit stays authoritative. Tested; verified live through nginx. |
| Proxy and Host trust (Phase 14) | Client addresses (throttles, quotas, audit) come from `X-Forwarded-For` only when the TCP peer is in `NAS_FORWARDED_ALLOW_IPS` (default `127.0.0.1`, passed explicitly to uvicorn; empty ignores the headers). The nginx example overwrites the header with `$remote_addr`; a spoofed value sent through it was replaced in the live test. `NAS_TRUSTED_HOSTS` adds Host validation (400 for other names, with the security headers). Tested. |
| Transport and browser headers (Phase 14) | `Strict-Transport-Security` on HTTPS responses when `NAS_HSTS_MAX_AGE_SECONDS > 0` (the production template sets one year), `Permissions-Policy` denying camera, microphone, geolocation, payment and USB, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, no `Server` header from uvicorn. Cookie deletion (logout) repeats `Secure`/`SameSite`/`HttpOnly`. Tested. |
| Bounded CSRF parsing (Phase 14) | The CSRF middleware reads a form body only for small (≤ 64 KiB, declared length) urlencoded forms. Multipart requests must send `X-CSRF-Token`; before Phase 14 a multipart request without it was buffered in memory in full (up to the upload cap) and then refused anyway. Tested. |
| Production configuration warnings (Phase 14) | At startup in production: cookie not Secure, `NAS_DEBUG=true`, empty `NAS_TRUSTED_HOSTS`, `NAS_FORWARDED_ALLOW_IPS=*`, drop folder without a rate limit. Tested. |
| File modes (Phase 14) | Every entry point (web, worker, helper) applies at least umask `027`, so the database, logs and caches are never world-readable even outside systemd. The throttles cap their tracked keys (10,000) so a flood of addresses cannot grow memory without bound. Tested. |
| Unit sandbox (Phase 14) | Web and worker additionally get `DevicePolicy=closed`, `SystemCallErrorNumber=EPERM`, `RemoveIPC`, `KeyringMode=private`, `LimitNOFILE` and `TasksMax` (`systemd-analyze security`: 1.4 "OK"). The helper gets `WorkingDirectory`, its own data/log settings (journal only), `RestrictAddressFamilies=AF_UNIX AF_NETLINK`, `IPAddressDeny=any`, `RestrictNamespaces`, `MemoryDenyWriteExecute`, `@mount` in its syscall filter, and deliberately **no** mount-namespace options so its mounts are visible on the host (exposure 4.9 → 4.3). Its run directory is `0711`. All three ran live under systemd 255: web and worker as uid `nas-manager` with `CapEff=0` and `NoNewPrivs=1`. |
| Dependency scanning (Phase 14) | `pip-audit` (pinned in `requirements-dev.txt`) against `requirements.txt` and `requirements-dev.txt`: no known vulnerabilities (2026-11-03). Re-run before each release. |
| Audit coverage (Phase 13) | Every state-changing API route records an event or is a listed exemption (read-only previews/lookups, resumable chunks), enforced by a test. Permission denials are audited (throttled to once per user, permission and endpoint per minute). Audit exports are themselves audited and neutralise spreadsheet formulas. Rolled-back actions never reach the logs. |

## Operational guidance

- Run the web service behind a TLS-terminating reverse proxy (`deploy/nginx/nas-manager.conf`) and keep the template's `NAS_SESSION_COOKIE_SECURE=true`, `NAS_FORWARDED_ALLOW_IPS=127.0.0.1` and `NAS_HSTS_MAX_AGE_SECONDS`; set `NAS_TRUSTED_HOSTS` to your host names. The service warns at startup about each unsafe production choice. Firewall everything but the proxy (and Samba on the LAN).
- Create the first administrator with `sudo /opt/nas-manager/deploy/nas-manager-cli bootstrap-admin` after install; there is no web endpoint that creates accounts before login.
- After each install or upgrade run `deploy/smoke_test.py`; before each release run `pip-audit -r requirements.txt`.
- Treat API tokens like passwords: create one per device with only the scopes it needs, keep the default expiry, and revoke lost devices from Profile → My API tokens (admins: the API tokens page). Tokens travel in a header, so serve the API over TLS only.
- Guard `/etc/nas-manager/nas-manager.env` (root:nas-manager, 0640) — it is sensitive once `NAS_SESSION_COOKIE_SECURE` and other production overrides are set.

- Back up the credentials key file (`NAS_CREDENTIALS_KEY_FILE`) together with the database, and store it separately from database-only backups: whoever holds both can decrypt every remote credential. Losing it means re-entering every remote credential.
- Use dedicated, least-privilege remote accounts for sync (an SFTP user confined to its directory, an S3 key limited to one bucket/prefix, an app password for WebDAV). Verify SFTP fingerprints out of band before trusting them.
- Preview (dry-run) a job before enabling it, especially two-way jobs.

- Backups: keep each repository passphrase outside the NAS (password manager or paper). Keep at least one repository off the machine. Use a remote account that can only reach the backup folder; it needs delete rights inside it for retention. Run a full **Verify** regularly and rehearse a restore. The `system` snapshots contain the credentials key: anyone with the repository *and* its passphrase can decrypt stored credentials, which is the reason for the passphrase.

- Photos often carry GPS coordinates in EXIF. Anyone who can browse a library sees them in the gallery and in downloaded originals (originals are never modified). Grant shared libraries deliberately; strip location data on the camera or phone if it must not be shared.
- Media and its cache: `NAS_MEDIA_DIR` holds user data and belongs in backups; `NAS_MEDIA_CACHE_DIR` is disposable. Keep `NAS_MEDIA_TRANSCODE_CACHE_MAX_BYTES` below the free space you can spare.

- Alert channels: use a dedicated SMTP account or app password, and set a webhook `signing_secret` so the receiver can verify `X-NAS-Signature` (HMAC-SHA256 of the raw body). Webhook URLs are chosen by administrators and may point at internal addresses (the same trust model as remote connections). Test each channel after saving it.
- A stopped worker cannot send notifications, including about itself. The Alerts page and dashboard show a "worker not running" banner from the web process, so watch the `nas-manager-worker` unit with your host's own monitoring if notifications are critical.

- Audit and syslog: prefer TLS destinations and a collector outside the NAS; with a plaintext destination, keep it on a trusted network segment. Watch the Logging page for a failing destination: until it recovers, audit events older than the retention period are not pruned (they stay in the database), and the backlog is sent when it comes back. The default retention is 90 days (`NAS_AUDIT_RETENTION_DAYS`; 0 keeps everything). A "chain broken" result is evidence, not something to "fix": compare the reported event with the collector's copy.

- Open the Disks page only with `NAS_HELPER_ENABLED=true` and the helper service running; otherwise discovery returns 503 and the page shows a "helper offline" badge. The helper socket lives at `/run/nas-manager/helper.sock` (`0660 root:nas-manager`, `SO_PEERCRED`-enforced); the service account UID must be listed in `NAS_HELPER_ALLOWED_UIDS`.

## Not yet implemented

Rotation of the credentials key and of backup repository keys, alerting on backup verify failures, TLS termination inside the app (use the reverse proxy), an independent watchdog for the worker (a dead worker cannot notify), per-user quotas for personal media libraries, EXIF/GPS stripping on download, album sharing, RELP (acknowledged syslog delivery) and mutual-TLS client certificates for syslog, and revoking other sessions when users change their own password. The resumable-upload lock, the bearer-failure throttle, the login limiter and the drop-folder rate limit are in-process (single web process; they reset on restart). Any local process can reach the app on loopback and, because loopback is the trusted proxy address, choose the client address it reports in `X-Forwarded-For` (local users are already on the NAS; the app is not reachable otherwise). Remote endpoints are administrator-chosen and not restricted to particular networks (an administrator can point a connection at an internal address). fstab persistence / auto-mount of disks is intentionally out of scope.

## Rules for later phases (from the project instructions)

- The web process must never run as root; privileged actions (e.g. reloading `smbd`, disk administration) go through the allowlisted helper, which never executes client-supplied commands. The Samba apply step delegates to the helper when enabled and otherwise stops at the boundary and reports `reload_required`.
- No automatic format, partition, destructive mount, erase or RAID rebuild. Read-only discovery by default; dry-run and explicit confirmation for destructive operations (Phase 5 implements both).
- Never delete data silently during two-way sync (Phase 7: sync never hard-deletes; see "Sync data safety").
- Public-upload quotas are keyed by client IP for anonymous clients and by token for API clients (Phase 6); the drop endpoint is rate limited per uploader before the body is read (Phase 14), and the nginx example adds a per-address limit in front.
- No plaintext passwords, API secrets or cloud credentials; exports must protect secrets; imports must be validated and reversible (Phase 12 implements both).
